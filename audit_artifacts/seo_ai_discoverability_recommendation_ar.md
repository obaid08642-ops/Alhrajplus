# تقييم معايير SEO وظهور الذكاء الاصطناعي لإعلانات الحراج بلس

> **النتيجة التنفيذية:** نعم، يمكن تطبيق الجزء الصحيح من هذه المنظومة تلقائيًا على **كل إعلان جديد** عند النشر والتعديل وتغيير الحالة. لكن لا توجد تقنية تضمن «التصدر» أو أن أي مساعد ذكاء اصطناعي سيقترح المنصة. الهدف الصحيح هو جعل كل إعلان **قابلًا للفهم والزحف والتحقق**، مع محتوى موثوق ومطابق لما يراه المستخدم، حتى يصبح مؤهلًا للظهور في Google ومحركات البحث والنتائج التوليدية. لم يُعدَّل كود التشغيل أو بيانات الإنتاج في هذا التقييم.

## الرأي في الملف المرفوع

الملف ممتاز من حيث الاتجاه العام؛ فهو يربط بين صفحات ويب مفهرسة، بيانات منظمة، بيانات تجارية محدثة، روابط عميقة، وسمعة المنصة. ومع ذلك، يحتاج إلى تصحيح في الأولوية وبعض التفاصيل قبل تنفيذه على سوق مبوب مثل الحراج بلس.

| البند في الملف | التقييم | القرار العملي للحراج بلس |
|---|---|---|
| JSON-LD من نوع `Product` و`Offer` | صحيح وعالي الأثر | ينفذ لكل إعلان نشط؛ مع بيانات حقيقية فقط: الاسم والوصف والصور والسعر والعملة والحالة والمدينة والبائع وحالة السلعة. |
| Merchant Center product feed | مفيد بشروط | ينفذ لاحقًا للفئات والتجار المؤهلين فقط، بعد مواءمة السياسات. لا يصلح تلقائيًا لكل إعلان P2P أو فئة منظمة/محظورة. |
| UCP وACP وMCP | صحيح تقنيًا، لكن ليس أولوية SEO | مسار شراء آلي متقدم؛ يؤجل إلى ما بعد اكتمال عرض الإعلان، الثقة، سياسة التاجر، والدفع والامتثال. |
| FAQ schema لكل إعلان | غير مناسب كأولوية | لا ينفذ تلقائيًا. أوقفت Google ظهور FAQ rich result في 7 مايو 2026؛ يمكن عرض إجابات حقيقية للمستخدم فقط، لا أسئلة وأجوبة مُولّدة أو مزيفة.[8] |
| Merchant return policy | مشروط | لا يضاف لصفقات P2P ما لم تكن للمنصة أو التاجر سياسة استرجاع مفروضة وحقيقية. |
| التقييمات والمراجعات | مشروط جدًا | لا يضاف `AggregateRating` إلا لتقييمات حقيقية قابلة للتدقيق؛ يمنع اختراع تقييمات أو مراجعات. |
| روابط عميقة وواجهات API | مفيد | يكمل عبر Android App Links وiOS Universal Links، مع مسار ويب عام مستقر لكل إعلان. |
| فتح الروبوتات | صحيح جزئيًا | نسمح للروبوتات المطلوبة في `robots.txt` وWAF؛ يجب إضافة `OAI-SearchBot` للظهور في ChatGPT Search، لا الخلط بينه وبين `GPTBot` الخاص بالتدريب.[4] |

تؤكد Google أن `Product` markup وMerchant Center feed معًا يزيدان أهلية المنتج لتجارب التسوق، لكن **عرض النتيجة الغنية واختيار ترتيبها يظل بقرار محرك البحث**. كما تشترط أن تصف البيانات المنظمة محتوى ظاهرًا ودقيقًا في الصفحة نفسها.[1] [2]

## الفجوة الأعلى أثرًا الموجودة حاليًا

هناك أساس جيد بالفعل: sitemap حي مع صور، وIndexNow، وملف `robots.txt`، ومسار خلفي يولد HTML وOpen Graph وJSON-LD لإعلان مفرد. لكن الاختبار الحي لمسار إعلان منشور (`/listing/...`) كشف أن الرد الأولي الذي يصل إلى المتصفح وGooglebot و`OAI-SearchBot` يعرض **بيانات عامة للمنصة**: canonical للصفحة الرئيسية و`Organization` JSON-LD، وليس عنوانًا أو وصفًا أو `Product/Offer` خاصًا بالإعلان. كما أن مسار الـHTML الخاص بالروبوتات موجود منفصلًا ولا يوجد ربط ظاهر له بالعنوان الأساسي للإعلان.

> لذلك فإن أهم عمل ليس إضافة Schema أكثر إلى endpoint مستقل؛ بل جعل **العنوان الأساسي نفسه لكل إعلان** يعيد HTML أوليًا مطابقًا لما يراه المستخدم، بمعلومات الإعلان الفعلية وcanonical صحيح وJSON-LD صحيح.

هذا ضروري عمليًا لأن Google توصي بأن تكون بيانات المنتج في HTML الأولي قدر الإمكان للبيانات سريعة التغير مثل السعر والحالة، وبأن تكون صفحة المنتج فردية ومحددة وليست صفحة قائمة.[3]

## ما سيحدث تلقائيًا لكل إعلان جديد

ينشأ مكوّن مركزي باسم `ListingSeoDocument` عند النشر أو التعديل أو تغيير الحالة. لا يختلق مكوّنًا لغويًا أو مواصفات؛ بل يحول حقول الإعلان التي يكتبها البائع ويقرّها النظام إلى وثيقة فهرسة موحدة.

| مرحلة دورة حياة الإعلان | الإجراء التلقائي المقترح |
|---|---|
| إنشاء مسودة | فحص العنوان والوصف والصور والمدينة والفئة والسعر؛ عرض اقتراحات جودة داخل النموذج فقط، من دون اختراع حقائق. |
| النشر | إنشاء slug ثابت وcanonical، وتوليد title وmeta description وOpen Graph وTwitter Card وJSON-LD وفق نوع الفئة، مع HTML أولي قابل للزحف. |
| تحديث السعر أو الصور أو الوصف | تجديد metadata وJSON-LD فورًا وإبطال cache الخاص بالصفحة وsitemap. |
| الإعلان النشط | إدراج URL في sitemap مع `lastmod` وصور مؤهلة، وإرسال IndexNow للمحركات التي تدعمه. |
| البيع أو الحجز أو الإيقاف أو الانتهاء | إزالة الإعلان من sitemap، تغيير `availability` بدقة أو إضافة `noindex`/إرجاع `410` للحذف النهائي حسب سياسة الاحتفاظ بالصفحة، وعدم إبقاء `InStock` ثابتة. |
| محتوى مخالف أو معلومات ناقصة | عدم الفهرسة حتى يستوفي الحد الأدنى، مع منع الفئات غير المؤهلة من Merchant feeds والشراء بالوكلاء. |

### بنية البيانات المنظمة الصحيحة

يستخدم كل إعلان نشط `Product` مع `Offer` كقاعدة، ويضاف النوع الأكثر تخصيصًا عند توفر بياناته فعليًا. إعلان السيارة مثلًا يمكن أن يجمع `Product` و`Car`، وإعلان العقار يستعمل النوع الملائم للعقار، وإعلان الوظيفة لا يستخدم `JobPosting` إلا إذا كانت جميع حقوله الجوهرية متوفرة. لا يُسجل أي حقل غير ظاهر أو غير موثق للبائع.

تشمل الحقول الأساسية: `name`، و`description`، و`image`، و`url`، و`sku`، و`category`، و`itemCondition`، و`offers.price`، و`priceCurrency`، و`availability`، و`seller` و`areaServed`. وتضاف العلامة التجارية أو رقم GTIN أو الشحن أو الاسترجاع فقط عند وجودها حقًا. أضافت Google في يوليو 2026 دعم `Product.category` المتسق مع Merchant Center، وهو حقل مناسب لإعلانات المنصة المنظمة.[8]

## اللغات الست: ما الذي يلزم فعلًا

تغيير لغة واجهة التطبيق وحده لا يكفي ليظهر الإعلان في كل لغة. Google تحدد لغة الصفحة من **المحتوى المرئي**، وتوصي بعناوين مستقلة لكل نسخة لغة ووسوم `hreflang` متبادلة عندما تكون هناك نسخ مترجمة فعلًا.[6] [7]

| اللغة | مسار النسخة المقترح | شرط الإدراج في الفهرسة |
|---|---|---|
| العربية `ar` | `/ar/listing/{slug}` | المحتوى الأصلي أو ترجمة عربية معتمدة. |
| الإنجليزية `en` | `/en/listing/{slug}` | عنوان ووصف وحقول فئة مترجمة فعليًا ومراجعة الجودة. |
| الأوردية `ur` | `/ur/listing/{slug}` | ترجمة حقيقية ومحتوى RTL متطابق في الحقائق. |
| الهندية `hi` | `/hi/listing/{slug}` | ترجمة حقيقية، لا مجرد واجهة هندية فوق وصف عربي. |
| البنغالية `bn` | `/bn/listing/{slug}` | ترجمة حقيقية ومراجعة لتفادي المعنى الخاطئ. |
| الفرنسية `fr` | `/fr/listing/{slug}` | ترجمة حقيقية تتوافق مع البلد والسعر والقيود ذات الصلة. |

كل نسخة مستقلة تضع canonical لنفسها ووسوم `hreflang` إلى جميع النسخ بما فيها نفسها، إضافة إلى `x-default`. لا ننشئ ست صفحات مترجمة آليًا ذات جودة ضعيفة؛ فذلك قد يكرر محتوى غير مفيد ويضعف الثقة. البدء العملي الأفضل هو العربية والإنجليزية للإعلانات الكاملة، ثم توسيع اللغات الأخرى بعد بناء مسار ترجمة ومراجعة يضمن دقة مواصفات السلع والأسعار والحالة.

## الظهور في البحث والذكاء الاصطناعي

يساعد هذا التنفيذ في التغطية والفهم، ولا يضمن الاختيار في إجابة ذكاء اصطناعي أو المركز الأول. فعليًا، ترتيب الأولويات هو كما يلي:

| الأولوية | التنفيذ | الأثر المتوقع |
|---|---|---|
| 1 | HTML أولي خاص بكل إعلان عند عنوانه الأساسي | أعلى أثر على إمكانية الزحف والفهرسة وفهم الإعلان. |
| 2 | metadata وJSON-LD دقيقان ومطابقان للمحتوى | أهلية أفضل لنتائج المنتج الغنية والتجارب المعتمدة على البيانات.[1] |
| 3 | sitemap متزامن وIndexNow وSearch Console | اكتشاف أسرع ومراقبة لأخطاء الفهرسة؛ IndexNow ليس ضمانًا للفهرسة في Google. |
| 4 | صور أصلية واضحة وalt text وعناوين ووصف غنيان بالحقائق | يفيد البحث والصور والنتائج التوليدية؛ لا يستخدم حشو الكلمات. |
| 5 | صفحات لغات حقيقية و`hreflang` | يوجه المستخدم إلى النسخة اللغوية الأنسب، ولا يضمن ترتيبًا عالميًا.[6] |
| 6 | `OAI-SearchBot` والروبوتات الموثوقة | يسمح بالوصول؛ OpenAI توضح أن `OAI-SearchBot` هو الخاص بظهور المواقع في ChatGPT Search.[4] |
| 7 | Merchant Center feed للفئات المؤهلة | يزيد فرص تجارب Shopping عند استيفاء الحساب والسياسات والبيانات.[1] |
| 8 | UCP/ACP | جاهزية للبيع داخل واجهات وكلاء الذكاء الاصطناعي، وليس بديلًا عن SEO. المساران يتطلبان حسابات/شراكات وcheckout آمنًا.[9] [10] [11] |

لا ينبغي التعامل مع `Google-Extended` على أنه زر ترتيب: Google تنص على أنه للتحكم في التدريب والـgrounding في Gemini، وليس إشارة ترتيب في Google Search.[5] كما أن ملف `llms.txt` اختياري لخدمات أخرى، ولا يمثل عامل ترتيب في Google Search.[8]

## خطة تنفيذ آمنة مقترحة

| المرحلة | المخرجات | ضوابط الجودة |
|---|---|---|
| 1. تصحيح المسار المفهرس | SSR أو prerender موثوق لمسار `/listing/{slug}` نفسه، مع 200/404/410 صحيحة | مقارنة HTML للمستخدم والروبوت، اختبار canonical وOG وJSON-LD لكل حالة. |
| 2. مولد `ListingSeoDocument` | Template موحد يشتق metadata وschema من حقول الإعلان والفئة والحالة | اختبارات وحدات لكل فئة وحالة، ومنع القيم المختلقة. |
| 3. دورة حياة الفهرسة | sitemap، Image sitemap، cache invalidation، IndexNow، وعمليات الحالة | اختبار نشر/تحديث/بيع/حذف مع sitemap وstatus code. |
| 4. اللغات | تخزين ترجمات مراجعة ومسارات `/ar|en|ur|hi|bn|fr/` وhreflang | تدقيق متبادل للـhreflang، منع فهرسة ترجمة غير مكتملة. |
| 5. القياس | Search Console وRich Results Test وURL Inspection وسجل جودة الإعلانات | قياس الانطباعات والنقرات والصفحات المفهرسة قبل/بعد، من دون وعود ترتيب. |
| 6. التجارة بالوكلاء | feed آمن للفئات المؤهلة، ثم تقييم Merchant Center وChatGPT feeds وUCP/ACP | فصلها عن إعلانات P2P الحساسة، وتطبيق امتثال ودفع وتفويض قبل أي checkout. |

## ما لن نفعله

لن نضع تقييمات أو سياسات استرجاع أو مخزونًا أو خصائص منتجات غير صحيحة. ولن نستخدم حشو كلمات أو محتوى مترجمًا ضعيفًا أو cloaking مختلفًا في المعنى بين الروبوت والمستخدم. كما لن نفتح APIs للشراء أو الدفع لوكلاء الذكاء الاصطناعي قبل نظام تفويض وموافقة صريحة وحماية ضد إساءة الاستخدام.

## التوصية النهائية

الملف قابل للتنفيذ **بنسبة كبيرة**، لكن التنفيذ الصحيح للحراج بلس يبدأ بصفحة الإعلان الفردية المعيارية وmetadata الخاصة بها، لا بالـUCP أو FAQ أو توليد ست نسخ لغوية عشوائية. بعد علاج الفجوة الحية الحالية، يمكن جعل النشر الجديد يحدّث كل عناصر SEO تلقائيًا وبشكل دقيق. ثم نبني الترجمة الحقيقية وfeeds والتكاملات المتقدمة على هذا الأساس.
