# التحقق الحي من إصلاح Backend للمراسلة وسجل المكالمات

**التاريخ:** 2026-08-20

## نتيجة إعادة النشر

بعد أن نفّذ مالك الخدمة إعادة النشر في Render، أعاد `GET /api/health` الاستجابة التالية:

```json
{"status":"ok","db":"connected","uptime":0}
```

قيمة `uptime` الصفرية وقت الفحص تثبت أن عملية Backend أعيد تشغيلها للتو، واتصال MongoDB متاح.

| فحص آمن على الخدمة الحية | النتيجة | الدلالة |
|---|---:|---|
| `POST /api/chat/send` بلا رمز دخول | `401` | مسار الإرسال منشور ومحمي بالمصادقة، ولا يوجد خطأ توجيه أو 404. |
| CORS preflight لـ`POST /api/chat/send` من `https://www.alhraj.online` | `200` | يسمح بـ`Authorization` و`Content-Type` ورؤوس عقد العميل، وكذلك `POST`. |
| WebSocket بلا رمز دخول | `403` | رفض متوقع وآمن؛ المصادقة مطلوبة قبل ترقية الاتصال. |
| صحة Backend | `200` | الخدمة وقاعدة البيانات متصلتان بعد إعادة النشر. |

## ما أصبح على الخدمة

إصلاح commit `5b614d3` يتضمن إنشاء محادثة وجلسة مكالمة عندما تكون دعوة الصوت أول تفاعل بين الطرفين، ومن ثم حفظ سجل المكالمة كرسالة نظام. كما يمنع فشل الإشعار أو Push للمستلم غير المتصل من تحويل رسالة تم إدراجها بالفعل إلى خطأ HTTP للمستخدم المرسل. ويتضمن كذلك تصحيح فهارس MongoDB غير المدعومة التي ظهرت في سجل النشر.

## حد التحقق الآمن

لم يتم إنشاء رسالة أو مكالمة تجريبية في الإنتاج. اختبار سلوك المستخدم النهائي الآن يتطلب حسابين مختلفين؛ هذا هو الاختبار التالي المطلوب: يرسل الحساب الأول نصًا للحساب الثاني ثم يبدأ اتصالًا بلا رسائل سابقة. ينبغي أن يظهر في سجل Render سطر `[chat] message persisted` عند الرسالة، وأن تظهر رسالة نظام مكالمة في المحادثة للطرفين عند بدء الاتصال أو انتهاءه أو عدم الرد.
